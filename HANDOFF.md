## Восьмой заход: файл пользователя с номерами формул (2026-09-23)

Задача: `deepseek_markdown_20260923_a5f70f.md` (в папке Google Drive рядом с «РАЗДЕЛ 1…»)
не давал PDF. Отчёт: «сборка не дала PDF — первая ошибка: Package amsmath Error:
`\tag not allowed here`», за ней «Undefined control sequence», «Missing number, treated as
zero», «Illegal unit of measure». В файле 37 нумерованных формул (`\tag{1}`…`\tag{37}`).

Разбор по шагам (каждая причина проверена отдельной сборкой):

1. `\tag` внутри `aligned` — две формулы из 37 приходят из markdown как
   `\[ \begin{aligned} … \tag{6} \\ … \end{aligned} \]`; amsmath разрешает номер только
   в самой выключной формуле и на этом роняет сборку. Проверено минимальными примерами:
   `\[ x=1, \tag{1} \]` и `align*` с `\tag` собираются, `aligned` с `\tag` — нет.
2. Номер в боксе подгонки: `shrink_displays()` (шаг для широких формул) измеряет формулу
   в `\hbox` и сжимает через `\resizebox` — там `\tag` тоже запрещён. Эта ступень
   включалась из-за переполнения в *абзаце* и переписывала все выключные формулы разом.
3. `\resizebox` даёт `graphicx`, а шаблон pandoc его не подключает: ступени сжатия формул
   и таблиц падали с «Undefined control sequence» — то есть лечение одной беды ломало
   сборку другой. На широкой таблице это воспроизвелось отдельно.

Что сделано в `convert.py`:

- `fix_inner_tags()` — `\[ \begin{aligned} … \end{aligned} \]` с номерами переводится
  в `align*` (строки те же, номера остаются на полях); то же для `$$…$$` — эту форму
  выключки можно встретить в написанном руками `.tex` (проверено отдельным файлом);
- `shrink_displays()` — формула с номером измеряется по версии, где номер переписан
  текстом (`\qquad\text{(6)}`), а если по ширине проходит, остаётся исходный вид с настоящим
  `\tag`; номер сам содержит формулу (`$…$`) — формула не трогается;
- `ensure_resizebox_support()` — `graphicx` подключается ровно тогда, когда `\resizebox`
  в тексте появился;
- `soften_inline_math()` — новая ступень: строка с длинной цепочкой инлайн-формул уходила
  за поле на 129 пт (в реальном документе это абзац про «Обобщённый алгоритм генерации…»);
  `\allowbreak` после запятых верхнего уровня даёт TeX точку разрыва, запятые внутри групп
  и между цифрами (`3,14`) не трогаются;
- занятый выходной файл (открыт в Word/просмотрщике) больше не даёт сырую `PermissionError`:
  `не удалось обновить <имя>.docx: файл занят другой программой — закройте его и повторите`.

Проверено: файл собран обоими форматами (`1 из 1 без ошибок`, PDF 22 страницы A4, 52 тыс.
знаков, кириллица ищется, в текстовом слое все 37 номеров формул; DOCX — 538 формул Word,
3 таблицы). Страницы просмотрены по снимкам — проблемные места (абзац с формулами, формулы
(6), (11), (12)–(15), матрица (16), таблицы, последняя страница) выглядят обычно: ничего
не обрезано, номера на полях, таблицы в пределах полей. Соседний файл «РАЗДЕЛ 1…» (тот, рядом
с которым лежал `.latex.log` от прежней неудачи) собран в PDF и DOCX. `selfcheck.py`
и `check_gui.py` — зелёные. Понятные сообщения про занятые файлы проверены искусственной
блокировкой (WinAPI с запретом записи). `PDFConv.exe` пересобран после этих правок.

Найденное и не тронутое: в корне проекта лежит `probe.docx` от чьей-то проверки.

## Седьмой заход: вход .docx и формулы MathType → Markdown (2026-09-22)

Задача: отдавать научные документы MathType мне в виде `.md` с формулами LaTeX. Разведка
(предыдущие разделы) показала: pandoc docx-читатель понимает только OMML; MathType-текст
`$…$`/`\[…\]` в docx он не парсит; штатный транслятор MathType не знает кириллицы и в
пакетном режиме молча теряет формулы (доказано на реальном фрагменте диссертации:
7 формул → 5, потеряны (1.33) и (1.34), причина — «No translation available for 0x043D»).

Сделано:

- `src/make_mathtype_translator.py` — генерирует `LaTeX Cyrillic.tdl` (LaTeX-транслятор
  + 66 кириллических правил, вывод `\text{...}`); пользователь установил его в
  `Translators\`, после чего Convert Equations перевело ВСЕ формулы, включая Р_накр;
- в `convert.py`: входной формат `.docx` и выходной формат **md** (галочка «Convert to»,
  по умолчанию выключена, для .docx включается сама). Маршрут: pandoc docx→json AST →
  `restore_docx_math` (склейка рун, многоабзацных `\[…\]`, инлайн `$…$`, чистка
  `% MathType!...`, предупреждения об одиноких номерах формул, сохранение OMML-абзацев) →
  `cleanup_math_code` (`\rm`→`\mathrm`, греческие команды → юникод) → pandoc json→markdown
  → `merge_char_texts` (склейка `\text{...}`) + NFKC. Картинки — `--extract-media` в
  `<имя>.media` (имя без пробелов) рядом с итоговым md;
- PDF из .docx: тот же md → markdown-маршрут; `.mark`-выделения из PDF-версии убираются
  (soul ломает кириллицу под xelatex), media копируется в каталог сборки (latexmk ищет
  картинки от cwd); DOCX из .docx — «нормализация»: MathType-текст становится формулами Word.

## Четвёртый заход: MiKTeX 26.5 требует Perl (2026-09-22)

Самопроверка на этой машине показала красную строку «Пробная сборка LaTeX»:
`pdflatex: ...\MiKTeX\miktex\log\latexmk.log | For more information, visit:
https://miktex.org/kb/fix-script-engine-not-found`. Файлы MiKTeX при этом на месте, и даже
`latexmk.exe` находится — то есть опять «наличие файлов ≠ работоспособность».

Разбор: с версии **MiKTeX 26.5** `latexmk` — это Perl-скрипт (`scripts/latexmk/latexmk.pl`),
а интерпретатор Perl **не входит** в дистрибутив MiKTeX (это же сказано и в справке MiKTeX по
ссылке выше). На машине Perl не было ни в одном виде. Проверено руками: `pdflatex.exe`
и `xelatex.exe` собирают тестовый документ напрямую, а `latexmk.exe` падает с `The script engine
could not be found. Data: scriptEngine="perl"`.

Что сделано:

- поставлен **Strawberry Perl 5.42.3.1 (portable)** в `C:\Tools\strawberry-perl` — portable-сборка
  не требует прав администратора; каталог `perl\bin` добавлен в пользовательский `PATH`
  (реестр `HKCU\Environment`, затем `WM_SETTINGCHANGE`), после чего `latexmk --version`
  печатает «Latexmk, John Collins, 9 March 2026. Version 4.88»;
- в `convert.py` добавлены `script_engine_missing()` и `script_engine_hint()`: проверка окружения
  теперь в этом случае пишет строкой «что сделать» совет поставить Perl, а не общую рекомендацию
  про автоустановку пакетов; `build_latex` добавляет ту же подсказку в ошибки конвертации;
- это описано в `CONTEXT.md` (п. 13 «Известных проблем», п. 5 про `cmap` и таблица требований),
  `README.md` (установка Perl) и `AGENTS.md` (внешние зависимости и ловушки).

Заодно нашлась вторая, тихая беда — в самом конвейере: `prepare()` подключал `cmap` **после**
`fontenc`, поэтому `cmap` писал «fontenc already loaded - some fonts may be unprocessed»
и T2A-шрифты оставались без обратного соответствия. Итог: PDF из `.tex` собирался без ошибок,
но кириллица в нём извлекалась как `Ïðîâåðêà ñáîðêè` — не искалась и не копировалась.
Проверки этого не ловили: заголовок набран другим шрифтом и читался, поэтому `verify_pdf`
находил в тексте кириллицу и молчал. Что сделано: `cmap` теперь вставляется **до** `fontenc`;
в пробную сборку добавлена проверка читаемости текста (`pdf_text_readable`: слово «Проверка»
должно находиться в пробном PDF от pdflatex и xelatex), а `pdf_text_hint()` объясняет причину,
если она не сойдётся. Проверено на двух вариантах одного и того же пробного документа:
со старым порядком проверка краснеет, с новым — зелёная; `.md` и `.tex` из пути с кириллицей
конвертируются без ошибок, в текстовом слое находятся слова из тела документа.

Проверено: `C:\Tools\Scripts\Python314\python.exe src\selfcheck.py` — все восемь проверок зелёные, итог «всё на месте,
конвертация проверена»; без Perl (в окружении, где его нет в `PATH`) отчёт теперь прямо говорит
причину вместо общей рекомендации. Копируя папку на другую машину, Perl нужно поставить и там.

`PDFConv.exe` пересобран (`src\build-exe.cmd`, PyInstaller 6.22.3): иначе в нём остался бы
прежний `convert.py` — с дефектом `cmap` и без новых подсказок. Новый exe весит 32 МБ вместо 85
(см. «Окно и exe» ниже, почему). Проверен в пустой папке — только exe и `bin\pandoc`, Perl в
`PATH`: `.md` и `.tex` без `fontspec` собрались в PDF и DOCX, все восемь строк проверки окружения
в журнале зелёные, а в PDF из `.tex` кириллица ищется («Проверка exe: кириллица и формула»).

## Ограничения (осознанные)

- Выходная папка не выбирается: результат всегда рядом с исходником.
- DOCX — стандартные стили pandoc; своего шаблона (`reference.docx`) пока нет.
- Входные форматы `.md`, `.markdown`, `.tex`, `.latex`, `.docx`. pandoc умеет больше
  (`.html`, `.rst`, `.org`) — добавить можно одной строкой в `SUPPORTED_SUFFIXES`.
- Кастомные макросы LaTeX в DOCX зависят от читателя pandoc: простое (`\newcommand` с
  `\texttt`) переносится, сложные пакеты могут потеряться.
- Проверка DOCX структурная (zip + XML), без Word: визуально документ не открывался.

## Что можно сделать дальше

- `reference.docx` под стиль заказчика (титул, шрифты, поля) — тогда DOCX будет «фирменным».
- `--resource-path` и копирование картинок при конвертации в DOCX.
- Выбор выходной папки в окне и запоминание последнего каталога.
- Поддержка `.html`/`.rst` как входных форматов.
- Для PDF: опциональное оглавление (`--toc`) и нумерация формул.
